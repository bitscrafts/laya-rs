# laya-rs — architectural review (2026-10-01)

**Reviewed tree:** `b0ee704` on `master`, clean at the start of the review. Read-only throughout:
nothing in `/projects/laya-rs` was written. A separate session modified
`_docs/06-research/04-jev-typesafe-ai-video-review.md` at 23:34 during this review; that edit is
not mine and was left untouched. All scratch work is under `/projects/_tmp/laya-analysis/`:
`notes/` holds raw outputs; `bench/`, `repro-graph/`, `repro-gate/` and `repro-store/` are
standalone crates that path-depend on the repo's crates.

**Baseline, re-measured:** `cargo test --workspace` gave **414 passed, 0 failed** (25 result lines).
`cargo clippy --workspace --all-targets -- -D warnings` exited 0 (`notes/baseline-*.txt`).

## Verdict

**The engineering is better than most, and the project is in worse shape than the brief implies,
for one reason: the safety gate.** The code quality is high. Errors are mostly typed, lints are at
zero, the head is reproduced against PyTorch to 4e-6, and the docs are honest about what they
measured. But the component whose wrong answer is irreversible answers **`allow`** for
`mkfs.ext4 /dev/sda1`, `shred -u secrets.txt`, `chmod -R 000 ~`, `> important.txt`,
`curl … | sh`, and *"Wipe the entire disk and delete all backups permanently"*, measured live
through the real `laya-mcp`. The `ask` tool then **executes** what the gate allowed. I proved this
on canary files: a file truncated to 0 bytes, and a file shredded. HANDOFF records this defect
class as "fixed (do not regress it)". It was narrowed to 12 substrings, not fixed.

Below that, the scheduler breaks its own fail-fast promise in a way its test cannot see, a
declared node `timeout` is silently ignored, the ledger cannot join a run to its decisions, and
the 26.5M-parameter Rust head, the project's flagship, takes 10.6 s per call and is not on the
production path at all.

Everything below carries `file:line` evidence. Every claim marked **[measured]** was run, and its
raw output is in `notes/`. Claims marked **[static]** come from reading the code only. §7 lists
what I could not verify.

## 1. Critical review

### Where the design is sound (briefly)

- **The graph owns the edges.** The `on` grammar is member access only (`on_expr.rs`). A `decide`
  lowers to `mcp` + `route` with the fallback last (`lower.rs`). That is a real, enforced property,
  pinned by spec 07 part 1 R5 with a control.
- **Crate boundaries hold.** `laya-core` has no I/O deps (`crates/laya-core/Cargo.toml`).
  `laya-graph` depends on neither `laya-mcp` nor `laya-store` (`crates/laya-graph/Cargo.toml`).
- **The head port is exemplary.** It is differential against the real torch modules
  (`crates/laya-head/tests/forward_differential.rs:46`, `LOGIT_TOL = 1e-4`, worst 4.05e-6), the tokenizer has exact
  parity, and `safetensors.rs:363-375` bounds-checks the header length before allocating.
- **`ask_file` scope** canonicalises and then does a component-aware `starts_with`
  (`crates/laya-core/src/ask_file.rs:161-170, 194-202`). Traversal and sibling-prefix cases are
  tested (`:309-341`).
- **Ledger single-writer** (B4) is designed correctly: segments are appended by servers, and
  `compact` is the only redb writer. Compaction is idempotent by identity (`crates/laya-store/src/lib.rs:193-201, 544-549`).

### 1.1 P0: the gate fails open, and `ask` executes what it allows **[measured]**

| evidence | what it shows |
|---|---|
| `crates/laya-core/src/agentic.rs:319-356` | `destructive_signals` = 12 case-sensitive substrings + a `push`/`--force` check |
| `notes/repro-gate.txt` | **NO SIGNAL** for `rm -Rf build`, `rm  -rf build` (two spaces), `rm --recursive --force build`, `rm${IFS}-rf`, `git clean -fdx`, `shred -u`, `> f`, `mkfs.ext4`, `chmod -R 000 ~`, `git push origin +main`, `git branch -D main`, `sed -i d config.toml`, `python3 -c "…rmtree…"` |
| `crates/laya-mcp/src/lib.rs:603-606` | `model_decision = policy.gate(answer.confidence, …)`. The noul **label is never read** |
| `notes/gate-live.txt`, `notes/gate-live-2.txt` (real `laya-mcp`, stdio) | **allow**: `> important.txt` 0.9071 · `shred -u secrets.txt` 0.9166 · `chmod -R 000 ~` 0.9017 · `curl … \| sh` 0.9939 · `mkfs.ext4 /dev/sda1` 0.9480 · "Wipe the entire disk…" 0.9207. **ask**: `ls -la /tmp` 0.8314 · `git status` 0.8722 · `cargo test` 0.8327 |
| `crates/laya-mcp/src/lib.rs:847-873` then `:878-884` | `ask` runs `sh -c <command>` **before** `compose_state` validates the request. There is no timeout on the child |
| `notes/ask-live.txt` (canary dir from `mktemp -d`) | `ask {command:"> important.txt"}` took the file from 14 to **0 bytes**. `ask {command:"shred -u secrets.txt"}` **removed the file**. Both calls then returned error `-32602 "ask has nothing to judge"` |

**Why the two-signal fix did not work.** Spec 04 F6c (`specs/04-mcp-server-and-ledger.md:50-62`)
requires *both* signals to be clear. One signal is a denylist. The other was measured, in the same
paragraph, at 6/12 with **negative separation**. AND-ing a denylist with noise gives a denylist,
and a denylist fails open on everything nobody listed. The live numbers confirm it: the model
scores destructive commands *higher* than benign ones.

**Two more latent defects on the same path [static]:**

- A confident **"no"** is allowed. A noul's confidence is `max(p, 1-p)` (`policy.rs:246`), so
  p(safe) = 0.05 gives confidence 0.95, which `Policy::gate` maps to `Allow` (`policy.rs:274-275`).
  No live "no" was obtained: all 15 probes returned `label=yes`.
- `irreversible` is **still decorative**. `policy.rs:279-280` has two identical `Mid` arms. Spec 04
  F6d says this was "corrected"; the correction moved the decision elsewhere and left the flag
  inert. Mutation testing confirms it: both `irreversible → true` and `→ false` **survive**
  (`mutants/mutants.out/missed.txt`).
- `Policy::gate` uses `band()` (choice thresholds), not `band_for(Noul, …)` (`policy.rs:274` vs
  `:249-260`). The defaults are equal (`:166-169`), so this is latent. `Band::Low → Deny` is also
  unreachable for a noul under the defaults, because confidence ≥ 0.5 = `low_threshold`.

**Fix (spec 08):** `allow` requires a positive allowlist match, with shell metacharacters
defeating any match. The model may only downgrade. `ask` validates everything before it executes,
with a deadline.

### 1.2 P1: the scheduler's fail-fast does not stop queued siblings **[measured]**

- Spec: *"siblings not yet started are not started"* (`specs/07-graph-executor-part3.md:81-83`).
- Code: `spawn_ready` spawns every ready node immediately (`sched.rs:207-226`), and
  `run_one` waits on the fan-out semaphore (`sched.rs:238`). On failure only *future* spawns stop
  (`sched.rs:180-189`), and no flag is checked after the permit is acquired.
- Repro (`notes/repro-graph.txt`), limit 1, independent nodes, `a` fails:
  `stopped_early=true failed=Some("a") records_after_failure=["a","b","c","d","e"]`.
  With `writes: true` nodes, that is four repository edits after the run already failed.
- Why the test missed it: the R11 test is a chain (`sched.rs:603-630`), where indegree alone blocks
  `n3`, so a scheduler with no fail-fast at all passes it.

**Also reproduced:**
- A cyclic `Graph` passed to the public `run` returns `Ok`, `stopped_early=false`, `records=["z"]`.
  The cyclic nodes vanish silently (`graph.rs:106-110` has public fields; `sched.rs` has no cycle check).
- A non-string `payload.<field>` aborts `run_flow` with `Err` (`route_exec.rs:266-276`), whereas a
  failing `decide` call is data with `stopped_early`. The same fault class is reported two ways **[static]**.

**Fix (spec 09).**

### 1.3 P1: deadlines that do not fire

- **Node `timeout` is ignored [measured].** `flow.rs:135-137` parses it, `GRAPH-SPEC.md:84`
  documents it, and no executor reads it (only `render.rs:33` lists it, as a *dropped* field).
  `notes/timeout-flow.json` declares `timeout: 1` around `sleep 3`; `laya graph run` reported
  `success:true, duration_ms:3002`, `completed`.
- **The shell executor is unbounded [static].** `node.rs:62-64` calls `std::process::Command::output()`
  inside `spawn_blocking`.
- **The MCP client's timeout does not bound the call [static].** `mcp_client.rs:38,114` bounds the
  channel read. The error path then does `drop(stdin); let _ = child.wait();` (`:239-241`) and
  never calls `kill()`, so a truly hung `laya-mcp` blocks forever.
- **The sidecar call blocks the whole server [static].** `PREDICT_TIMEOUT = 2 min`, hardcoded
  (`crates/laya-backbone/src/sidecar.rs:43`), runs synchronously on a current-thread runtime
  (`crates/laya-mcp/src/main.rs:72-74`). That makes it the server's only latency SLO, and it is 2 minutes.

**Fix (spec 10).**

### 1.4 Performance: three measured costs, and one that is not a problem

| what | measurement | where |
|---|---|---|
| Head forward, release, real checkpoint | **0.70 s @ seq 32 · 2.82 s @ 128 · 10.64 s @ 460**; cold load 0.149 s | `notes/bench-head.txt`; `math.rs:207-218` single-accumulator `matvec`, per token |
| Same FFN shape, tiled 8 tokens × 8 accumulators | **1.641 s → 0.244 s (6.7×) single-threaded**, max \|diff\| 9.8e-7 | `notes/bench-head.txt` |
| `compact`, per inserted row | **2.51 → 3.42 → 3.92 → 4.70 ms/row** as the store grows 0 → 1500 rows (O(n·m): `insert_if_new` rescans every identity, `crates/laya-store/src/lib.rs:544-549`, plus one write txn per row) | `notes/repro-store.txt` |
| `laya-mcp` spawn per graph `mcp` node | **~25 ms** (39–47 ms including ~17 ms of Python harness) | `notes/mcp-spawn-cost.txt`. **Not worth optimising** against a 173–436 ms decision |

**A recorded root cause is wrong [measured].** `forward.rs:456-467` and HANDOFF:104-107 attribute
an O(seq³) slowdown to *"`chunks_exact(..).nth(..)` … a LINEAR scan"*. `ChunksExact::nth` is O(1):
10⁶ random-index calls take 0.003 s (`notes/nth-measure.txt`), and the pre-fix code
(`git show 4f807d0^:crates/laya-head/src/forward.rs:455-482`) used exactly that. The real costs are
the scalar strict-order reduction (`math.rs:214`: *"the reduction order is part of the contract"*)
and the missing weight reuse across tokens.

**How to measure going forward:** spec 12's `examples/forward_bench.rs` (real checkpoint, median of
3, exits non-zero over budget, with a control proving it can fail). For the store, the
`repro-store/` harness pattern: ms/row as a function of store size, where flat means O(1) per insert.

### 1.5 Ledger data correctness **[static]**

- `bucket_clamped` is copied from `saturated` (`crates/laya-mcp/src/lib.rs:742-745`). Two different facts
  (B2 clamp vs saturation) are stored in one column. Calibration by bucket would be wrong.
- `confidence … .unwrap_or(0.0)` (`lib.rs:722-725`): a missing confidence is recorded as 0.0, a
  valid-looking value that poisons ECE.
- `run_id: None, node_id: None` always (`lib.rs:714-715`); `head_sha256`/`backbone_sha256` always
  `None` (`:740-741`).
- Only `decide` records (`lib.rs:1328`, single call site). `gate` and `ask`, the decisions that
  matter most, leave no trace.
- With `LAYA_LEDGER_DIR` unset, recording is skipped silently (`lib.rs:705`).

### 1.6 Architecture-level: the flagship is not on the production path

`laya-mcp`'s `Cargo.toml` does not depend on `laya-head`. Every MCP decision, and therefore every
graph `decide` (via `LiveMcpCaller`), goes `laya-mcp → Python sidecar` (`ServerState.sidecar:
laya_backbone::Sidecar`, `lib.rs:183`). The Rust head is reachable only through `laya decide`
(`crates/laya-cli/src/decide.rs`), which is used for the parity harness. The design's headline,
*"the whole decision layer can be Rust with no Python and no torch"* (HANDOFF:457-460), is proven
**possible** and is **not done**. Meanwhile the sidecar is unsupervised (HANDOFF:394-395) and
strictly serial (HANDOFF:396).

### 1.7 Hermeticity: "414 green" depends on the network **[measured]**

`crates/laya-graph/tests/acceptance.rs:72-80, 91-110` asserts a reachable backbone and a prebuilt
sibling `laya-mcp` under plain `cargo test`. In cargo-mutants' clean copy, the baseline failed on
exactly that (`mutants.baseline-failed/…/baseline.log`: `panicked at …acceptance.rs:107:5`). This
contradicts AGENTS rule 9 (*live tests kept separate*). Note that `verify-all.sh` step 7c already
handles the live run separately (`scripts/verify-all.sh:144-155`).

### 1.8 Stale or false documentation **[measured against the tree]**

- `HANDOFF.md:239-243` says *"laya-store declares no dependencies … redb is absent from
  Cargo.lock"*. In fact `crates/laya-store/Cargo.toml` depends on `redb`, which `Cargo.lock`
  lists, and the same file contradicts it at `:143-161`.
- `AGENTS.md:147-156` "Current state (2026-09-29)" says five crates are "scaffolds only", which is
  false since spec 03/04.
- `HANDOFF.md:192-216` "THE SAFETY DEFECT THAT WAS FIXED" is contradicted by §1.1.
- `forward.rs:456-467` and HANDOFF:104-107 give the wrong root cause (§1.4).

The project's own rule is *"never erase a superseded claim — annotate it"*. Each of these needs an
annotation, not a rewrite.

## 2. Observability: where the system is blind

**What exists:** `RunReport { run_id, stopped_early, failed_node, worker_limit, records }` and
`NodeRecord { run_id, node_id, success, exit_code, output, error, duration_ms }`
(`crates/laya-graph/src/run.rs:19-64`); a ledger row with 20 fields (`crates/laya-store/src/lib.rs:93-144`);
`ledger stats` with overall p50/p95/max (`:807-823`); `laya doctor` probing `/health`,
`/v1/models` and the head socket (`crates/laya-cli/src/main.rs:74-117`). No crate uses `tracing`/`log`.
`laya-mcp` has 10 free-text `eprintln!` calls (`main.rs` 9, `lib.rs:666` 1).

**The 3 a.m. questions, and whether they can be answered today:**

| question | today | why |
|---|---|---|
| Which decision sent run R down branch B? | **no** | the run's route record has the value; the ledger row has `run_id: None` (`lib.rs:714`) |
| What did the gate allow in the last hour, and did `ask` execute it? | **no** | `gate`/`ask` never write the ledger (`lib.rs:1328` is the only call site) |
| Is the run slow because nodes are slow, or because `limit` starves them? | **no** | `duration_ms` starts after the permit (`node.rs:63,109`); no queue wait |
| Is the ledger even on? | **no** | silently off when `LAYA_LEDGER_DIR` is unset (`lib.rs:705`) |
| p99 decision latency per tool; gate allow ratio | **no** | `Stats` is global, p50/p95/max only |
| Which head/backbone produced this decision? | **no** | `head_sha256`/`backbone_sha256` always `None` (`lib.rs:740-741`) |
| Did a node time out, or fail? | **no** | no timeout exists (§1.3) |

**Proposal (spec 11), in order of value:**
1. **Propagate `(run_id, node_id)` end to end**: `McpCaller::call(&CallContext, …)` to `decide`'s
   args to the `DecisionRow`. This is the single join that turns two logs into one story.
2. **Record every judgement**, gate and `ask` first, with `gate_decision`, `model_decision`,
   `destructive_signals` count, `executed`, and `command_sha256`, never the command itself.
3. **Node timeline**: `queued_ms`, `started_at_ms`, plus `wall_ms` on the run. Fan-out utilisation
   is `Σ duration_ms / (wall_ms × limit)`; starvation shows as `queued_ms` > 0.
4. **One JSON event line per tool call** on `laya-mcp` stderr (`seq` as request id, `tool`,
   `run_id`, `latency_ms`, `outcome`, `decision`), plus a startup `ledger` event.
5. **Per-tool `stats`**: p50/p95/p99, gate allow/ask/deny, `executed` count.

**`tracing` vs hand-rolled:** `tracing 0.1.44` is already compiled in (`Cargo.lock:1244`, via
`rmcp`), but **`tracing-subscriber` is not in the offline registry**. Spans also do not cross the
stdio boundary without the propagation in (1) anyway. Recommendation: hand-roll (4) now, about 40
lines, using event and field names that map one-to-one onto `tracing` events. Adopt `tracing` when
a collector exists. Do not add a subscriber for stderr alone.

**What the acceptance test should assert so this cannot regress:**
`the_ledger_row_joins_the_run_report`. Run the R-ACC fixture with `LAYA_LEDGER_DIR` set to a
tmpdir, then assert that exactly one row has `run_id == report.run_id`, `node_id == "classify"`,
and `label ==` the route record's `value`. This is the observability equivalent of the existing
two-fixture routing proof, and it fails today.

## 3. Traits: where they pay, and where they do not

| current concrete type | proposed trait | methods | what it buys | verdict |
|---|---|---|---|---|
| `laya_backbone::Sidecar` in `ServerState` (`crates/laya-mcp/src/lib.rs:183`) | `Judge` | `fn predict(&self, state: &Value, questions: &Value) -> Result<Value, JudgeError>` | (a) **offline tests of every tool's success path**, which today can only test the *down* path by pointing at a nonexistent socket (`lib.rs:1711-1714`); (b) the swap to an in-process `RustHead` impl (§6) behind one seam; (c) spec 08/11 tests with fixed answers | **pays: build it** |
| `McpCaller` (`crates/laya-graph/src/node.rs:47-54`) | keep it, change its signature | `fn call(&self, ctx: &CallContext, tool: &str, args: &Value) -> Result<String, CallError>` | run-id propagation (spec 11); typed `Timeout` (spec 10) | **pays: amend** |
| `Option<PathBuf>` ledger dir + `append_segment` (`lib.rs:705, 748`) | `DecisionSink` | `fn record(&self, row: &DecisionRow) -> Result<(), StoreError>` | "ledger off" becomes an explicit `NullSink` instead of a silent `?`; tests assert on a `MemorySink` instead of reading files | **pays, modestly**; do it with spec 11 |
| `Embedder` (`crates/laya-head/src/end_to_end.rs:122-144`, `run<E: Embedder>`) | exists | n/a | already the right seam: HTTP backbone in prod, fixtures in tests | **sound as is** |
| `execute_shell` (`node.rs:62`) | `ShellRunner` | n/a | one implementation, and tests use a real `sh` | **over-abstraction** |
| clock (`SystemTime::now` in `lib.rs:793`, `Instant` in `node.rs`) | `Clock` | n/a | `ReadinessCache` already takes `now_ms` as a parameter (`readiness.rs:239,252`). Parameters beat a trait here | **over-abstraction** |
| `Ledger` over redb | `Store` | n/a | single-writer is a redb property the design depends on; a trait would hide it | **over-abstraction** |
| `Policy` | n/a | n/a | it is data (thresholds, allowlist), loaded from TOML (`policy.rs:186`) | **keep as data** |
| tokenizer | n/a | n/a | one implementation, pinned by exact differential | **over-abstraction** |

**Pure functions beat traits for the gate.** Spec 08's `gate_verdict(command, model, irreversible,
&Policy)` in `laya-core` makes the whole safety decision testable with zero I/O. No trait is needed.

## 5. Where the specs are over- or under-specified

**Spec demanded something wrong (beyond the two already recorded: the store dependency in
`07-graph-executor.md:225-228` reversed at `part3:140-146`, and the timeout that could not fire,
`part2:121,130-133` vs `expand.rs:415-438`):**

1. **Spec 04 F6c encoded a fail-open gate** (`04-mcp-server-and-ledger.md:57-60`). It AND-ed a
   denylist with a signal the same paragraph measured as noise. This is the most expensive spec
   error in the repo (§1.1).
2. **Spec 03 rejected parallel matmul on two false premises** (`03-rust-head.md:180-190`): that it
   needs `unsafe` or a dependency (`std::thread::scope` needs neither), and that it breaks
   determinism (row partitioning does not). It then estimated ~755 ms using L = 192
   (`:172-176`) while the head sees up to 512 tokens. Measured: 10.6 s at 460.
3. **Spec 06 demanded a queue** that the architecture made unreachable (CODE-REVIEW C1). It is now
   honestly marked "deliberately unwired".

**Under-specified (a future implementer will guess):**
- `timeout` is documented in `GRAPH-SPEC.md:84` and parsed by part 1, but **no part of spec 07
  assigns its enforcement**. So nobody enforced it and nothing refused it (§1.3).
- R11's *"running siblings are cancelled at their next checkpoint"* (`07-graph-executor.md:172-173`):
  "checkpoint" is never defined, and part 3 quietly narrowed it (`part3:157-158`).
- R9 has no default `limit` (`07-graph-executor.md:160-163`).
- Spec 04's ledger has no requirement that *non-`decide`* tools record, so `gate`/`ask` do not.
- No spec says what a route value of the wrong JSON type does (§1.2).

**Over-specified:** criteria that grep source for crate or feature names (`part3:218-220`
`rt-multi-thread`, `part2:161` `blake3`). The tally: part 1 5/16, part 2 5/16, part 3 9/23,
part 4 3/14 criteria are source greps. They pass on a broken implementation that spells the
dependency right and fail on a correct one that does not. Prefer a behavioural test plus, at most,
one grep with a control.

**Criteria that pass on broken code:** R11's chain-only test (§1.2), and spec 04's gate criteria,
which have no destructive corpus.

## 6. My opinion, plainly

- **Biggest risk:** the gate. It is live in Hermes (`HANDOFF.md:280-281`), it answers `allow` to
  `mkfs` and `curl | sh`, and `ask` will execute what it allows. Everything else in this report is
  a refinement; this one is an incident waiting for a trigger. Ship spec 08 before any other work,
  and until it lands, treat `ask`'s `command` argument as disabled: if no client can be restarted,
  have the caller never pass it.
- **Biggest missed opportunity:** the Rust head is proven correct and is not in the product. The
  project's thesis (Rust, no Python, no torch, one binary) is one `Judge` trait plus one ~10× kernel
  fix away. That would remove the unsupervised, serial Python sidecar, which is HANDOFF's top open
  item (`:370-372`), from the hot path. Specs 12 and then a `RustHead: Judge` spec get there.
- **Best value per effort:** spec 08 R1–R3 plus the live corpus script. It is about a day of work
  (a pure function, an allowlist field, a reorder in `ask`) and it closes the only irreversible
  failure mode in the system. If the gate is held to be out of scope, the next best is spec 09 R1:
  one `AtomicBool`.
